# GLaDOS Quick Deploy 1.2.1 使用指南

适用：Windows 10/11 x64、macOS 13 及以上的 Apple Silicon 与 Intel Mac。本版保留 1.2.0 的七项功能，并修复结果读回、错误分类与进度显示问题；安装包已经包含运行组件与官方 GitHub CLI。

## 1. 已有用户：覆盖安装并更新全部部署

1. 完全退出旧版。Mac 打开相应 DMG，把其中的 `GLaDOS Quick Deploy.app` 拖到原安装位置并选择替换；Windows 运行新版安装器并选择原目录。
2. 保留原数据目录。只替换实际正在使用的 `.app` 或原 Windows 安装目录；如果应用已放在 `/Applications`，就替换该处的同名应用。曾使用 MacData 的用户应保留 `/Volumes/MacData/Applications/GLaDOSQuickDeploy/Data`。首次打开新版、识别旧数据时须保持原磁盘挂载；已有定位记录时，程序按保存的位置继续读取。不要因换了应用位置而删除原 Data。
3. 打开新版，在“现有账号”检查账号与原设置，再到“设置与诊断”点击 **一键升级全部云端配置**。应用按仓库读取全部账号清单、保留各账号已有设置与登录 Secrets、更新工作流并读回验证。已完成的仓库重复升级不会重复改写。
4. 需要补签时点击 **全部签到**。需要查询最新账号信息但不签到时点击 **更新账号信息**。只想读取已有执行结果时点击 **读取已有结果**。

升级保留账号、备注、设置、待办和原数据位置。旧单时间转换成时间列表，例如原来的 12:30 保留为 12:30，不自动重置为默认值。覆盖安装本身不使网站已经失效的登录重新有效；只有对应账号明确要求更新登录时才需要重新登录。

程序沿用原 App ID 与系统安全存储身份。第一次创建或解密新版账号报告时，系统可能要求钥匙串授权；普通启动没有待恢复加密文件时，不会为该空文件初始化钥匙串。已有 `data-location.v1.json` 定位记录时，原数据目录离线或不可访问会停止读取，不切换到空账号库；尚无定位记录的首次识别依赖当时可见的旧数据，因此须连接原磁盘。发现原数据文件损坏时会停止加载并保留文件。换电脑、换系统用户或丢失系统加密密钥不属于同机覆盖升级。

### 三个功能页面

- **现有账号**：日常签到、账号信息、读取已有结果及账号设置。卡片的“编辑设置”分为签到计划、积分兑换和启用状态；“账号详情与更多操作”包含登录更新、云端运行链接和本机备注。
- **新增账号**：登录和首次部署、恢复未完成任务、独立部署进度。首次表单设置一个每日时间；部署后在“现有账号”的“编辑设置”中调整为总共 1–6 个每日时间，包含原来的主时间。
- **设置与诊断**：统一更新全部云端配置、仓库清理与保活设置、运行记录和可复制的安全诊断。

三个页面分别保留自己的进度与提示。GitHub 设备授权码出现在发起操作的页面；账号管理操作不会覆盖新增账号的部署结果。点击账号“更新登录”时，会进入新增账号页面继续该账号的登录任务。

## 2. 本版七项功能

| 功能 | 使用方式与结果 |
| --- | --- |
| 多次定时与冗余 | 每账号设置 1–6 个时间；前一时点未运行或明确临时失败时，后续时点仍可执行。今日已有成功证据不会重复签到。 |
| 替换应用继承数据 | 应用与账号数据分开保存；覆盖原安装位置，保留原数据文件夹。 |
| 部署后修改设定 | 在账号卡片选择“编辑设置”，或勾选多个账号后点击“编辑所选账号”，修改时间、兑换方案、启用状态。 |
| 状态与账号信息 | 区分今日签到、任务进度、兑换结果；显示积分、剩余天数、采集时间与运行链接。 |
| 独立三天清理 | 每日独立 Cleanup 工作流清理超过 72 小时的本应用运行及附件；保留正在运行和近期重跑的任务。 |
| 一键升级全部云端配置 | 按已管理仓库逐个升级全部账号，读回一致才标记成功；部分失败单独列出。 |
| 全部账号签到 | 对管理范围内启用的账号逐个处理；暂停账号跳过；请求编号和进度可恢复。 |

同仓库最多 100 个账号，最多 100 个不同定时时点。账号设置相互独立；新账号使用部署表单的初始值，不覆盖其他账号已经保存的独立设置。

## 3. 设置多个签到时间与兑换规则

账号卡片选择“编辑设置”，时间使用 24 小时制，以逗号分隔，例如：

`12:30, 18:37, 22:13`

所有时间按台湾时间／北京时间 **UTC+8**。相同时间去重，不同账号可以使用不同时间。第一次部署的初始时间是 09:30；升级会保留旧时间，需要冗余时可勾选账号后点击“编辑所选账号”，加入备用时点。保存设置只更新所选账号，写入后读回一致才显示生效，不额外触发签到，也不要求重新登录。

| 兑换选项 | 触发条件 |
| --- | --- |
| 关闭自动兑换 | 仅签到，不使用积分兑换。 |
| 100 积分换 10 天 | 已确认今日签到且查询到的积分足够时尝试。 |
| 200 积分换 30 天 | 同上，使用对应套餐。 |
| 500 积分换 100 天 | 新部署默认选项，使用对应套餐。 |

实际套餐可用性和结果以 GLaDOS 响应为准。查询不到积分不兑换。签到成功与兑换成功分开记录；兑换失败不会抹掉已确认的签到成功。兑换响应丢失或内容无法确认时，保留“待核实”并停止重复兑换；跨午夜或更新登录也不能证明上一笔兑换没有扣分。新一天仍可正常签到。

多条定时都运行在 GitHub Actions 上，能够提供多次执行机会，但 GitHub 调度延迟、平台停用或网站登录失效仍需按实际提示处理。配置存在、手动任务成功和真正观测到 schedule 触发是三种不同状态；界面不会把它们混为“定时验收通过”。

## 4. 分清查询、签到与停止

**读取已有结果**只读取 GitHub 中已经存在的配置、运行和报告；**更新账号信息／更新信息**只向 GLaDOS 查询账号状态与积分，不发签到或兑换；**全部签到／签到**才提交签到任务。在“更多账号工具”中，**加载积分与会员信息**会尝试读取已有账号报告，并使用本机保存的报告密钥显示详情。

批量任务按仓库逐个处理，单个仓库错误单独记录，不把其他仓库的结果一并记为失败。正在处理时按钮防止重复提交；网络响应不确定时保留原请求标识，再次继续优先查找原运行，不把请求接受当成签到成功。

批次可以停止并保留进度，之后明确继续同一批次；停止后后台不再发送该批次尚未提交的请求。已经交给 GitHub 的运行可以继续完成。签到批次与信息查询批次不能互相冒用；需要切换任务类型时先处理界面显示的原批次。对于长期未确认请求，按界面提供的结束入口处理后仍保留防重记录；这不会把原请求标成成功，也不会立即补发同日签到。

需要暂停日常定时任务时，在账号设置中关闭该账号的启用状态。手动全部签到也跳过停用账号。仓库在 GitHub 中整体关闭 Actions 会影响整个仓库，升级按钮不会擅自解除这一关闭状态。退出 App 或关机不会删除已经部署的云端任务。

## 5. 如何判断签到结果

| 显示 | 含义 |
| --- | --- |
| 今日签到成功／今日已签到 | 有该账号、UTC+8 今天的已确认签到结果。新增积分为 0 仍可能是有效签到。 |
| 云端已接受请求、排队、正在执行 | GitHub 已接收任务或正在执行，业务结果尚未确认。 |
| 云端运行已结束，账号结果待确认 | 已确认原运行结束，但 APP 尚未取得该账号完整回执；读取已有结果会继续核对原任务。 |
| 提交结果待确认 | 原请求的响应不确定，保留原请求标识；不会直接重复提交。 |
| 未获取、结果待核实 | 接口或报告没有提供可核实数据，不会用 0 或历史值冒充实时结果。 |
| 需要重新登录 | 当前网站会话被拒绝；在对应账号卡片选择“更新登录”。 |
| 签到成功，兑换失败／待核实 | 签到已确认，兑换另行显示；避免重复扣分。 |
| 尚未观察到 schedule | 尚无真正的定时触发记录；手动运行不能代替这项证据。 |

账号面板显示全部计划时间、下次计划、最近执行、积分、当日观测新增积分、剩余会员天数、兑换方案及信息采集时间。昨天的成功不会显示为今天成功。运行记录可打开对应 GitHub Actions 页面。

邮箱、余额与报告明细在云端加密，公开运行日志和匿名回执不含 Cookie、完整邮箱或余额详情。没有本机原报告私钥时，可以继续管理部署和查看匿名结果，但不能凭空恢复加密详情。

## 6. 每日清理与保活

清理是独立的 **GLaDOS Quick Deploy Cleanup** 工作流，默认 UTC+8 **03:43** 执行。每次固定一个 72 小时截止时间，完整收集列表后逐项核实再删除：

- 只处理本应用的签到、信息查询、清理和保活运行，不删除其他工作流。
- 运行须已完成，且创建、开始、最后更新均早于截止时间；当前清理任务、排队、执行中和近期重跑的任务保留。
- 删除运行会连带移除其附件；附件上传时也设置三天保留，仓库原生保留期写入后读回核实。
- 缓存只清理 `gqd-v2-` 专用前缀中超过期限且未近期使用的项，不处理通用 Python 或其他项目缓存。
- 无法确认已删除的项目记录为失败，界面显示最近结果及可核实删除数量。

每日清理执行之间可能暂存刚超过 72 小时的记录；它控制本部署产生的记录，不承诺其他仓库占用也全部消失。在“维护设置”可以修改清理时间及开关；“立即清理过期记录”使用同样的规则。

独立保活工作流默认每月 1 日 UTC+8 11:23 更新活动时间戳，用于减少公开仓库长期不活动后定时被停用的情况。保活不更新 Cookie、不代替官网登录，也不是补签。

## 7. 首次部署、添加账号与恢复

第一次使用时，进入“新增账号”，选择浏览器后点击“添加并部署账号”。如果需要，你在 GitHub 官方网页完成设备授权，在 GLaDOS 官方网页完成登录及验证；其余仓库创建、独立 Secret 配置、计划任务和首次结果读取由 App 接续完成。

已有未完成部署时，选择“继续未完成任务”，沿用原账号、GitHub 身份、仓库与设置。加入另一个账号使用“新增账号”入口或部署记录中的“添加账号”。更新已有账号使用其卡片上的“更新登录”，应用会核实是同一账号，避免覆盖另一个账号的登录记录。

应用优先使用识别到的 Brave，也支持应用内登录窗口。浏览器发现范围包含 Chrome、Edge、Firefox、Opera、Vivaldi、Chromium，以及 Mac 上的 Arc；实际可用性取决于安装位置和浏览器协议。Safari 可以参与 GitHub 网页授权，但不用于自动采集 GLaDOS 会话。应用内窗口无需额外浏览器扩展。

外部登录使用独立临时 profile，不接管日常浏览器资料；正常结束或取消后清理，暂被占用的本应用临时目录会在后续启动时重试。验证码与官网要求的验证由本人完成。

## 8. 数据文件与故障处理

| 数据 | 用途 |
| --- | --- |
| `deployment-state.json` | 原有账号、设置和不含 Cookie／Token 的部署检查点。 |
| `pending-deployments.enc` | 待上传的登录会话，由系统安全存储加密；默认七天期限，网站可能更早使其失效。 |
| `management-state.v2.json` | 已读取云端配置、账号结果、批次进度、本机备注、升级阶段与安全诊断。 |
| `report-keys.v1.json` | 报告公钥及经系统加密的私钥；不要删除后期待仍能解密旧报告。 |
| `data-location.v1.json` | 原数据位置的定位记录，防止磁盘变化后错误切换。 |

系统安全存储不可用时不会将 Cookie 或报告私钥改为明文保存。GitHub 会话仍由随包官方 CLI 管理。界面底部显示实际数据目录；Windows 或未使用 MacData 的电脑沿用系统应用数据位置。

| 情况 | 处理 |
| --- | --- |
| GitHub 权限不足 | 使用补充授权入口，以原 GitHub 账号完成官方授权；无需手工创建 Token。 |
| 云端配置发生变化 | 刷新后重新编辑，避免覆盖另一台电脑的更新。 |
| 一键升级部分未完成 | 查看本次阶段；“配置已核对，后续检查待完成”表示配置已确认，维护检查仍需继续。再次点击会接续核对；旧成功时间不算本次成功。 |
| GitHub 通用错误或结果读取中断 | 展开“查看安全诊断”并点击“复制诊断”。未明确证实授权问题时，不用反复重新授权。 |
| 网站要求重新登录 | 只更新对应账号；反复刷新旧会话不能代替有效登录。 |
| 原数据位置不可用 | 恢复原磁盘或目录权限，不要删除 Data 来建立空库。 |
| 钥匙串拒绝解密 | 保留现有加密文件与系统钥匙串，恢复正常凭据访问；不要重置整个钥匙串。 |
| 运行结束仍待核实 | 点击“读取已有结果”或打开对应运行，缺少业务回执时保持未核实。 |
| 安装来源提示 | 包含 macOS ad-hoc 签名，尚未 Apple 公证；Windows 无商业代码签名。核对随附校验值，按系统正常提示处理。 |

停止操作只停止本机当前步骤或等待，不撤销已经接受的云端运行。部署尚未提交时显示“停止部署”，已提交后显示“停止本机等待”；管理批次使用“停止并保留进度”，停止后剩余未提交的仓库不再自动发送请求。

1.2.1 的升级记录区分“本次尚未更新配置”“配置结果待核实”“配置已核对，后续检查待完成”和“本次升级已全部核对”。应用中断后会说明上次核对未完成，不把重启显示为正在后台升级。

安全诊断仅保留错误代码、失败环节、HTTP 状态、CLI 退出码、原因类别、请求方法与接口类别，不保存原始响应正文、完整 URL、Cookie 或令牌。旧版本没有保存的原始错误无法事后还原；历史通用错误会标明具体原因未记录。已修复一个可复现的问题：仅查询账号信息、尚无当日积分记录时，旧版读回逻辑可能抛出异常；本版保留未知值，不填成 0，也不把查询当签到成功。此问题不能单凭旧截图认定为历史错误的唯一原因。

正式交付的构建验证记录区分逻辑测试、三平台原生打包启动／界面验证，以及真实账号业务运行。本次测试使用隔离样例，不把样例测试当成你的实际账号已签到，也不把手动运行当成定时触发验收。
