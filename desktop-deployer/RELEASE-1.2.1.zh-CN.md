# GLaDOS Quick Deploy 1.2.1 补丁说明

适用 Windows x64、macOS Apple Silicon 和 Intel。保留 1.2.0 的多次定时、覆盖安装继承数据、部署后独立账号设置、账号信息与签到状态、独立三天清理、一键升级全部配置及全部账号手动签到。

## 界面与操作

界面分为“现有账号”“新增账号”“设置与诊断”三个页面，各自显示进度、错误和恢复提示。常用账号操作为“全部签到”“更新账号信息”“读取已有结果”；前者签到，第二项向 GLaDOS 查询而不签到兑换，第三项只读取已有云端运行。账号的“编辑设置”按签到计划、积分兑换、启用状态分组；备注和登录更新放在账号的更多操作中。

“设置与诊断”保留“一键升级全部云端配置”，以及每仓库清理和保活设置。首次部署页面仍设置一个时间，部署后每个账号总共可设置 1–6 个每日时间，包含原来的主时间。新账号部署、原任务恢复、更新已有账号登录和批次停止功能均保留。

## 已确认并修复的问题

1. **信息查询成功后，本机仍可能报错。** 旧版在仅查询账号信息、没有当日积分记录的组合下可能访问不存在的本日积分对象。现在将缺失信息保留为未知，继续处理结果，不生成假积分或假签到。
2. **请求已被接受，但后续读取异常被当成操作失败。** 现在分别保存提交是否已接受、云端运行状态、账号回执是否核对、详情是否已取得。云端已结束但回执或详情待读取时，显示结果待确认；原请求标识和防重复提交保护保留。
3. **多个账号共享一次运行时，整次工作流失败影响单个账号判断。** 现在依据目标账号的结果判断；缺少该账号证据时保持待核实，其他账号的失败不会直接变成该账号失败。
4. **配置已经更新，后续维护读取异常仍显示笼统升级失败。** 现在保留本次配置读取、比较、提交、读回及维护核对阶段；配置已读回一致后即显示实际设置。配置核对完成、维护仍待检查与全部核验完成分开显示，旧成功时间不会用于证明本次成功。
5. **多个页面共用错误与进度。** 账号操作、部署和维护采用独立反馈，后台账号结果读取不会覆盖维护或新增部署提示。设备授权码留在发起操作的页面。
6. **通用 GitHub 错误缺少可排查信息。** 现在保存并展示安全诊断，并区分已确认的授权、权限、资源、限流、服务、传输等错误。符合条件的只读请求可有限重试；未确认原因的错误不会一律建议重新授权，也不会盲目重发签到请求。

## 如何读状态

| 显示 | 含义及下一步 |
| --- | --- |
| 本次尚未更新配置 | 本次配置修改尚未完成，可查看失败环节后继续核对。 |
| 配置结果待核实 | 修改响应或配置读回未完成，不能把它当成确定未修改。 |
| 配置已核对，后续检查待完成 | 云端配置已确认；继续执行维护与工作流核验。 |
| 本次升级已全部核对 | 本次配置及维护核验均已完成。 |
| 提交结果待确认 | 保留原请求；只查找和跟踪原任务，不重复发送。 |
| 云端正在执行 | 等待同一运行结束；可停止本机等待。 |
| 云端运行已结束，账号结果待确认 | 云端运行结束已确认，APP 仍需取得目标账号回执或详情。 |
| 今日签到成功 | 取得该账号今天的签到证据，查询任务和历史成功不会冒充该状态。 |

单个仓库读回受阻时，批次会保留它的状态和诊断，并按规则继续其他独立仓库；已明确仍在排队或执行的运行保持串行等待。停止本机批次后，不再提交剩余仓库。云端已接受的任务可能继续运行，停止本机等待不会撤销签到。

## 诊断边界

安全诊断只包含代码、环节、HTTP 状态、CLI 退出码、原因类别、请求方法、接口类别；不包含原始响应正文、完整 URL、Cookie、令牌或私钥。可以展开“查看安全诊断”后复制。

旧版历史记录没有保存原始错误，无法事后从一个 `GITHUB_COMMAND_FAILED` 还原唯一根因。上述问题已通过源码和隔离测试复现或验证，但不能断言旧截图中的每一次失败必然是网络、权限或某一个已修复缺陷。

## 安装与验证

完全退出旧版，替换实际使用的同名应用或原 Windows 安装目录，保留原数据目录和系统安全存储。首次打开新版、识别旧数据时须保持原磁盘挂载；已有数据定位记录时，原目录离线会停止读取，不切换到空账号库。安装路径变动不代表应该删除旧 Data。打开后先在“现有账号”核对数据，需要更新云端部署时到“设置与诊断”使用统一升级按钮。

发布验证包含逻辑测试与三平台原生启动、真实 renderer / preload / IPC 隔离验收。页面截图使用 `example.invalid` 样例账号，覆盖导航、按钮、错误隔离、授权码可见性与结果待确认状态；样例验证不代表用户真实账号已经签到。最终打包结果与校验值以随附构建验证记录为准。
